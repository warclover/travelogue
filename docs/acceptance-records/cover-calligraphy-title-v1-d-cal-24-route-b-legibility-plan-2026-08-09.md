## 0. 一句话结论

路线 B（字库合成，默认全量兜底路径）迄今只验收过「字形是否存在」（`fonts.py::glyphs_covered`），从未验收过「渲染后人眼是否读得懂」；而流量占比小、默认关闭的路线 C 反而有 `ocr_verify` 强制回读门禁（D-CAL-19）——验收力度与流量占比恰好错配。真实样本 `demo-0ebda73294`「初中毕业照」在默认字库 `ZhiMangXing`（钟齐志莽行书）连笔渲染下，"毕"字肉眼可读成"华"。**本记录提出 D-CAL-24**：给路线 B 补一层纯本地、零 LLM / 零网络的笔画连通性自检，命中风险字时静默切换到候选池内已有的备用字重，不改变路线 B「任何情况下必须可用」的红线,也不新增任何外部依赖。

## 1. 证据

样本来自 `docs/acceptance-records/attachments/cover-calligraphy-title-v1-w3-blind-2026-08-08/b01-art.png`（`band-cut`，trip 标题为「初中毕业照」，默认字库渲染）：

![band-cut「初中毕业照」默认字库渲染](./attachments/cover-calligraphy-title-v1-w3-blind-2026-08-08/b01-art.png)

第一遍目测把标题读成「初中**华**业照」——「毕」字在这款狂草连笔字体下笔画粘连严重，跟规整字体（如 `simhei`）里独立分离的三横+竖钩结构完全不同。这不是孤立的渐罩/配色问题（已有 D-CAL-23/`assume_dark_veil` 覆盖那类问题），而是**字体本身对特定汉字的笔画表现力风险**，此前从未被任何验收环节捕捉——83+ 条既有单测只覆盖字形覆盖率、对比度、位置、防溢出，没有一条覆盖"渲染出来的字人眼认不认得出"。

## 2. 与既有红线的边界核对（本记录的核心价值）

在展开机制设计前，必须先排除一个容易踩雷的方向：**不能**照搬路线 C 已经写好的 `ocr_verify.py`（调用 `travelogue.llm.client.vision_chat_completion` 多模态 LLM 接口）挂到路线 B 头上。

理由：D-CAL-01 / D-CAL-02 是冻结红线——

> 路线 B 锁定为默认兜底：字库合成 — **100% 本地 Pillow 渲染，零 LLM / 零扩散模型调用，任何情况下必须可用**。

若路线 B 的默认渲染路径需要一次网络 LLM 调用才能决定最终用哪款字体，即便把失败处理成"忽略校验结果，按原字体渲染"这种安全降级，也已经：

1. 在字面上违反「零 LLM / 零扩散模型调用」——校验本身就是一次 LLM 调用，不因为结果被忽略就不算数；
2. 给本该纯 CPU、毫秒级完成的路线 B 引入了一个**不可控的外部依赖**（网络延迟、API 配额、Key 是否配置）——这跟「任何情况下必须可用」的承诺直接冲突：路线 B 存在的意义之一就是在路线 C 彻底不可用（无 Key/断网/未开启）时仍能 100% 工作。

**结论**：D-CAL-24 的机制设计必须是**纯本地启发式**，不发起任何网络请求，不消耗任何 LLM Key/额度，不为路线 B 引入除 CPU 时间外的新依赖。这一条边界本身就是本次要钉死的决策，优先于具体算法选型。

## 3. 机制规格（提案，未实现）

- **触发点**：`render_b.py` 渲染主标题前，逐字符跑一次「连通域粘连度」启发式。
- **做法**：对当前候选字体（如 `ZhiMangXing`）取该字符在实际渲染字号下的 alpha mask，与 `fonts.py::FALLBACK_STACK` 中笔画分离度较高的规整字重（如 `simhei.ttf`）渲染同一字符的 mask 做连通域数量对比；候选字体连通域数显著低于规整字重（阈值待第 4 节小样本核对后钉死）→ 判定该字符「连笔粘连风险」。
- **命中处理**：整条标题只要有一个字符命中风险，`render_title_art` 对**这次渲染整体**切换到 `FONT_POOL` 中已有的备用候选——`鸿雷板书体（简+繁）3.001`（`licensed=True`，已随包分发，零新增授权/素材成本）。不报错、不询问用户、不展示提示——延续 D-CAL-16「静默降级」的设计语言，只是这次降级发生在路线 B 内部的字体选择这一层，而不是路线 C→B 那一层。
- **成本**：对 ≤8 字标题的全部字符各跑一次连通域计数，纯 CPU、零网络；预期单次渲染增加个位数至十位数毫秒（未实测，第 4 节验证）。

## 4. 验证与分阶段（低成本优先，呼应"成本最低"的选题初衷）

| 阶段 | 内容 | 成本 |
|------|------|------|
| **Phase 0**（本记录） | 决策边界 + 机制规格；不改代码 | 已完成 |
| **Phase 1** | **不写通用连通域算法**，先用**已经产出的 W1/W3 真实样本**（零新增素材成本）人工过一遍：拿已知问题字符（"毕"）和几个已知正常字符，分别用 `ZhiMangXing` 渲染，肉眼+简单像素统计核对"连通域数量差异"这个信号是否真的能把两类字符分开；同时人工核对切到 `鸿雷板书体` 后"毕"字是否确实更好认（备用字体更优只是假设，见 OQ-CAL-11，不能想当然） | 数小时，复用现有截图与字体资产 |
| **Phase 2** | Phase 1 验证通过后，阈值与备用字体候选定稿，接入 `render_b.py` 正式路径 + 补单测（比照 `test_title_art_fonts.py` / `test_title_art_render_b.py` 现有风格） | 需单独排期，不在本记录范围 |

## 5. 非目标

- 不对路线 C 做任何改动，`D-CAL-19` OCR 门禁保持不变。
- 不新增字体采购/授权流程——复用 `FONT_POOL` 中已有的 `licensed=True` 候选。
- 不引入 numpy/scipy 等新依赖；若 Phase 2 发现 Pillow 原生 API 无法轻量实现连通域计数，需另行评估并单独决策，本记录不预先批准新依赖。
- 不承诺"鸿雷板书体一定更可读"——这正是 OQ-CAL-11 的开放问题，留给 Phase 1 用眼睛核对。

## 6. Phase 1 结果（2026-08-09 · 已跑完）

### 6.1 方法

新增一次性验证脚本 [`scripts/title_art_d_cal_24_legibility_probe.py`](../../scripts/title_art_d_cal_24_legibility_probe.py)（不进生产路径）：

- 用纯 Python 8-邻接 flood fill（不引入 numpy/scipy，呼应 §5 非目标）对 7 个孤立汉字分别统计 `simhei`（基线规整字重）/`ZhiMangXing`/`鸿雷板书体` 渲染后的 alpha mask 连通域数量；
- 测试集：`毕`（真实样本里被误读的字）+ 6 个对照字（`业`/`照`——同样来自「初中毕业照」但**未**被误读；`华`——误读时脑子里冒出来的字；`斯`/`兰`/`藏`——泛化对照，`藏` 刻意选笔画多、结构复杂的生僻向字）；
- 同时渲染 `毕业`/`初中毕业照` 两个真实语境短语，供人工重新读一遍（呼应你提出的"人类对文字兼容性很高"这一质疑）。

### 6.3 结论：§3 提出的机制被证伪

**关键反例**：`业` 和 `照` 都是同一句真实标题里的字，且**均未**被误读，但它们在 `ZhiMangXing` 下的连通域比值（0.33 / 0.29）反而**低于**真正被误读的 `毕`（0.67）——按 §3 提出的"比值越低风险越高"规则，算法会把 `业`/`照` 判定为比 `毕` 更危险，跟真实误读情况正好排反。`藏`（刻意挑的复杂/生僻向字）比值 1.50，完全没有触发任何风险信号，尽管它笔画客观上最多。

**结论**：孤立单字的"候选字体 vs 规整字体连通域比值"这个信号，**不能**可靠区分"人类真的会读错的字"和"字体正常的艺术化连笔"——本质原因是草书连笔本身就会普遍降低连通域计数，这是这类字体的**设计常态**而非"缺陷特例"，用它当风险探测器噪声远大于信号，真上线会把大量正常、美观的连笔渲染错误地打成"高风险"触发字体切换，反而破坏路线 B 的书法美感（正是 D-CAL-02"越少干预越好"红线想保护的东西）。

### 6.4 结合你提出的"人类对文字兼容性很高"

补充一句更根本的反驳，比算法本身的问题更重要：**这条风险最初的"证据"，来自我作为旁观者、脱离上下文、逐字拼认地看一张截图**——这恰恰是人类阅读中最不常见的模式。真实场景里，标题是**用户自己写的**（"毕业照"对写这个标题的人是极强先验），封面下方还有小字重复了一遍原文（`docs/acceptance-records/attachments/.../b01-art.png` 图中确实有一行 `初中毕业照 · 1天` 的常规字体小字作为兜底），且人类读汉字向来靠词汇/词组级别的整体轮廓识别、靠上下文纠偏,而不是逐笔画拼认——本节 6.2 的语境短语渲染（`毕业`/`初中毕业照`）在有完整词组的情况下，肉眼核对比孤立单字更容易读顺，佐证了这一点。**孤立单字误读不能简单外推成"真实用户会看错自己的标题"**，我在决策记录 §1 的原始表述高估了这个风险。

## 7. 结论（更新）

**D-CAL-24：Phase 1 验证已完成，§3 提出的连通域启发式机制被数据证伪，且问题本身的风险被高估——建议关闭，不进入 Phase 2，不给路线 B 增加任何自动可读性门禁。** 保留本记录作为"设计一个启发式门禁前，先用几个反例证伪它"的方法论留痕；`OQ-CAL-11` 随之关闭（连通域比值不是可用信号，鸿雷板书体是否"更易读"这个问题在没有可靠判定机制的前提下无法回答，也不再需要回答）。若未来出现**真实用户**反馈"看不懂标题"（而不是产品内部人工核对时的自我怀疑），再针对具体字/字体组合做人工判断，不预先建自动化机制。
