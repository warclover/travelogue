## 0. 一句话结论

**砍的是 `mosaic` 这套搜索算法，不是游记这本书。**

编排收成一套（人编固定序列），画布降级成参数（竖版 / 16:9 / 3:4），模板与使用规范收进已有的 TDV 工坊并把升格闭环。游记作为「竖版全屏画布」保留，因为它服务的是分享/手机阅读，那是产品的常态接收端。

## 1. 触发：多轮实测后的产品判断

### 产品原话（大意）

经过多次实际测试，游记与作品集两个管线的差距不大，总体作品集输出效果更好；萌生只保留一条、把这一条继续做得更精致美观可靠的想法。

### 与 2026-08-27 备忘录的关系（重要）

上次否决的是「**保住两本书、把管线并成一条**」，本次提的是「**只做一种书**」。这不是推翻旧结论，而是触发了旧结论自己写好的前置条件——[作品集管线简化讨论备忘录.md](./作品集管线简化讨论备忘录.md) §3 结尾：

> 若接受只做一种书：才配开「一条管线、多种导出」。那是重签主产品。

代价明码标价：**重签主产品**（CHARTER §1 + §11）。

### 核实：代码比

| 管线核 | 文件数 | 行数 |
|--------|--------|------|
| `layout_engine/mosaic/**`（候选生成 / 打分 / beam / 前缀 beam / replan / 自愈） | 48 | **11,696** |
| `layout_engine/editorial_series/**`（选系列 / 分组 / 贴页 / 槽位匹配） | 9 | **2,298** |

**五倍代码量，换来一个产品认为反而更差的输出。这个比值本身就是结论。**

补记：双管线的隔离税（12 条窄缝、312 行 ownership lint、3 条 import-linter 契约、105 条 `pipeline_isolation` 用例）**大部分是已付掉的沉没成本**，现在是稳态资产。拿它当砍管线的理由说服力有限；真正刺眼的是上面这个比值。

## 2. 诊断：作品集为什么更好

### 三种可能，指向三个不同结论

| 可能原因 | 若成立，结论是 |
|----------|----------------|
| (a) 16:9 这个形态本身更像「作品」 | 保留形态、砍掉竖屏 |
| (b) `page-*.yaml` 就是做得更精致 | **模板工艺差距，可移植**，不构成砍管线理由 |
| (c) 固定序列的确定性 vs 搜索的方差 | 「搜索」对品味是错的目标函数，该砍的是算法 |

支撑数据：

| 模板族 | 文件数 | 总行数 | 平均行数/个 |
|--------|--------|--------|-------------|
| `screen-*.yaml`（游记） | **47** | 3,208 | **68.3** |
| `page-*.yaml`（作品集） | 76 | 10,203 | **134.2** |

> **§19 更正**：初版此表为 `73 / 5,951 / 81`，源于统计混入了 `dist/TravelogueStudio/_internal/` 下 26 个 PyInstaller 构建副本（47 + 26 = 73）。**更正后本节论点更强，不是更弱**——单模板均长差距由 1.68 倍升至 **1.96 倍**。详见 [§19](#19-代码核验后的更正2026-09-01)。

### 产品澄清（第二轮）

- 游记：**撑满屏幕、看大图很爽、更符合分享需求**
- 作品集：**细节控制更好、模板更精致、更符合审美需求**
- 「差距不大」指的是 **下限**：照片本来杂乱时两者几乎无区别
- 好照片集时 **游记反而会做出惊艳的输出**；作品集更多体现杂志感与艺术性

### 结论：搜索算法主动阻止了模板变精致

核实 `mosaic/candidates.py`：`generate_window_candidates` 按 aspect signature 取出一批候选 pattern，逐个做可排序性 / 几何 / 用量检查，活下来的进候选池打分比较，再交给 beam search 选序列。

这个结构对模板提了一个隐含要求：**每个 `screen-*` 必须能接住任意窗口的照片，必须能与兄弟模板互换比较。** 模板不知道自己会落在第几屏、前后是什么、这一章节奏走到哪——它只能做通用，而通用必然平庸。

平均 68 行 vs 134 行不是审美在几个月里进步了近一倍，是 **约束不同了**。固定 series 序列里每一页都知道自己的位置，所以可以针对位置精修：第一页写死是留白开场，第七页写死是双图对开，因为你知道它一定在那儿。

> **编排必须先变成人写的固定序列，模板才有被精修的资格。这两件事是同一件事。**

这正是产品自己得出的结论（「无论如何调整优化算法，都无法实现智能拼图和排版……最终落到模板和编排」）的架构含义：**只要搜索还在中间，模板想精修也修不了。**

### 推论：拼图从算法搬到模板

`editorial_series` 里 **零个 `collage`**，这不是缺失，是它不需要——槽位是人在 `page-*.yaml` 里编排好的。`mosaic` 侧的拼图逻辑（`candidates.py` / `compose.py` / `hero_six.py` / `clone_detection.py`）可整体退役，拼图变成竖版模板里写死的槽位编排。

**不是丢掉拼图，是把拼图从算法搬到模板。**

## 3. 修正：不是砍掉自由度，是降级自由度

产品第三轮补充了一条关键实测，它修正了 §2 的结论：

> 游记的模板粗糙一些，但被各类算法平衡了，达到一定的效果，拥有较好的容错率；作品集模板精致、下限更高，但没有游记灵活。

这是 **探索与利用的权衡**。若把 `mosaic` 整个砍掉，会 **同时失去容错率和天花板**——变成今天作品集的样子：下限高、上限平。

正确做法是把自由度 **从「搜索页序」降级到「选系列 + 匹配槽位」**：

| 层级 | 谁负责 | 今天的实现 |
|------|--------|-----------|
| **页序** | **人**（编排成册） | `series/*.yaml` 的 `sequence[]` |
| **选哪套系列** | 算法（粗粒度） | `match.py` · 按 kept 数选 `capacity` 档 |
| **往槽位放哪张** | 算法（细粒度） | `slot_match.py` · aspect / role / hero face / star upgrade |

容错率来自「系列选得对」，天花板来自「系列本身编得好」，而不是来自搜索的运气。

### 前置条件（顺序不能反）

**系列必须足够多样，否则「降级自由度」就等于「砍掉自由度」。**

### 更正上一轮的事实：系列已有 8 档，但只有一个维度

`editorial_series/series/` 下已有 8 个正式系列，不是 1 个：

| 系列 | pageCount | photo_span | capacity |
|------|-----------|------------|----------|
| `magazine-8-standard` | 8 | [24, 40] | 19 |
| `magazine-12-standard` | 12 | — | 29 |
| **`magazine-16-standard`**（P0 金样） | 16 | [48, 80] | 43 |
| `magazine-20-standard` | 20 | — | 65 |
| `magazine-24-standard` | 24 | [72, 120] | 67 |
| `magazine-28-standard` | 28 | — | 76 |
| `magazine-32-standard` | 32 | — | 88 |
| `magazine-36-standard` | 36 | — | 96 |

但 **8 档全部 `density: standard`、全部 `stage: "16:9"`**。它们只是 **厚薄，不是性格**。48 张和 80 张会选到不同厚度，但「人物为主的城市漫步」和「风景为主的徒步」会拿到完全一样的页序骨架。

所以「作品集不如游记灵活」的根因不是系列少，而是 **系列只有一个维度**。要补的是第二个维度，而不是从零编一套目录——工作量判断因此从「新建系列体系」降为「给现成的 8 档阶梯加一个维度」。

### 产品对「性格维度」的态度

以 **拍摄主体**（人物为主 / 风景为主 / 人景均衡 / 细节为主）为主，兼顾 **阅读节奏**（安静 / 标准 / 密集）。但产品明确指出：

> 本质上很难按一个维度来切，一定是多维度的共同作用，这也是算法的复杂性；曾尝试过多种算法组合，但效果很有限，或者没效果。

**这条实测非常重要**：它说明「多维度自动匹配」这条路已经试过并且失败过。因此性格维度不应做成又一套打分组合，而应做成 **少量、离散、人可命名的系列 SKU**，由 `match.py` 用尽可能粗、尽可能可解释的规则去选。宁可只有 4 种性格且选错时明显，也不要连续加权且没人说得清为什么是这一页。

## 4. 制作端与阅读端：一个被混淆的矛盾

### 产品原话（大意）

在 27 寸 2K 显示器上评测，没有在手机端操作和对比过；重心在 Web 端测试。承认矛盾：绝大多数用户用手机处理和观看照片，只有少量摄影爱好者用电脑处理排版；自己偏爱 Web 端是因为自己是摄影爱好者，设计思路会向自己这边偏。

### 纠正：这不是偏见，是两个角色被混在了一起

**制作端在电脑上是这个产品的必然属性，不是设计者偏见。** 输入是本地照片文件夹，手机用户从物理上就不是制作端用户。这是定位收窄（摄影爱好者、有相机、会把照片导进电脑），但内部完全自洽，不需要为它道歉。

**真正的问题不是「用户用手机」，是「接收方用手机」。**

产品自己给出的常态场景：

> 我是摄影爱好者，一同旅行的朋友可能不是。我在电脑端编辑好，把成果通过微信发给朋友，朋友们都在手机端观看。输出长图发到微信群，朋友用手机看；发到小红书，读者也在手机看。

> **电脑端编辑、手机端阅读，应该是最常态。**

### 证据缺口

| 事实 | 影响 |
|------|------|
| `portfolio-pages.css` 全文 2,362 行，**零个 `@media`**，只有写死的 `aspect-ratio: 16 / 9` | 作品集今天没有手机竖屏故事 |
| `journal-screens.css` 有 5 处 `@media` | 游记有（虽不完备） |
| 接收端（手机）**一次都没测过** | 「作品集更好」这个判断的最大偏差来源 |

产品自己的描述里已含答案：游记「更符合 **分享** 需求」——分享就是接收端。**这一项从未被算进「哪条更好」的打分里。**

这也让「两种画布」从妥协变成必需：**竖版全屏服务分享（微信、朋友、手机），16:9 服务桌面精读。** 它们是两个不同的需求，不是同一需求的两种做法。

## 5. 意外发现：`stage.variants` 是死声明

> # ⛔ 本节结论已失效（2026-09-01 代码核验）
>
> 「声明层已建好、缺的只是编译器、P0 是一处改动」——**这三句都是错的**。
>
> `stage.variants` 的 schema 只允许 `layout` 与 `aspect` 两个字段（`additionalProperties: false`），**不含任何槽位几何**；`models.py` 的 `TemplateStage` 根本没有 `variants` 字段，加载即丢弃；渲染层另有多处硬编码 16:9。
>
> 照本节原方案编译 variants，产出的是「把 16:9 网格塞进 9:16 盒子」的变形版式，**且会看起来像做完了**。
>
> **正确做法见 [§19](#19-代码核验后的更正2026-09-01)。以下内容仅保留作为推理过程与错误记录，不得作为实施依据。**

### 事实

- `layout_template.schema.json` L99–116 **已定义** `stage.variants`（可为 web/mobile 指定不同 aspect）
- 几十个模板 **已声明** 该字段，`page-*` 与 `screen-*` 都有。例如 `page-4-grid-land.yaml` L24–28 明确写了 `web: 16:9` + `mobile: 9:16`
- **`css_gen.py` 全文零次引用 `variants`**——它根本不读

### 后果

这些声明是死的：能过 schema 校验、能表达意图、**编译不出任何一行 CSS**。这就是 `portfolio-pages.css` 零个 `@media` 的直接原因——不是没人想过手机，是想过、写下来了、编译器没实现。

### 意义：这是重构最短的一刀

**「多个画布」的声明层已经建好了，缺的只是编译器。**

不需要新增第三种模板族。新增一族要动八处：`css_gen.template_family()`、schema 枚举、新 CSS bundle、`paths.py`、渲染层（`assemble.py` / `reading_profile.py` / `data-edition` / `dock.js`）、DPI 前缀 lint、工坊 packet 格式、导出运行时镜像。

而让 `css_gen` 认识 `variants`、把 mobile variant 编译成媒体查询块，是一处改动，且能同时拿到：

1. 作品集的手机可读性（补上 §4 的证据缺口）
2. 竖版画布的地基
3. 一个现在完全不知道的答案：**同一套 page 编排投到竖屏上，到底好不好看**

第 3 项决定后面要不要另编竖版系列。如果 variants 编译出来之后作品集在手机上已经能看，后续工作量少一大截。

## 6. 印刷：短期不做（已定）

### 产品原话（大意）

反复自问，答案是不要，至少短期内不要。作品集的输出仅提供 **印刷的输入**——用户自己打印装订，或把这套图片交给打印社二次加工，打印社不管排版只管打印设置，双方容易合作。否则制作画册非常麻烦：打印社不懂用户的逻辑和排版，用户不懂印刷社的要求。作品集管线主要面向希望自己留存电子版或偶尔打印的用户，**不做竞品那种电子书印刷的获客/盈利模式**。

### 推论（比预期更省）

这个决定把 16:9 从「**印刷载体**」降级为「**桌面阅读画布**」，于是出血、CMYK、跨页对齐、300dpi 那一整套东西全都不用碰。

既然产物是「交给打印社的图」，那就没必要绕一趟浏览器：**作品集的页图应该学 ECC，而不是继续拍预览 DOM。** `export/card_renderer.py` 已经证明这条路可行——Pillow 按模板槽位 cover-crop 后 paste 到画布，无浏览器无 DOM。

这与 [作品集管线简化讨论备忘录.md](./作品集管线简化讨论备忘录.md) §4 的「**页序真源、预览 HTML 降为投影**」同向，且印刷决定给了它更强的理由。

## 7. 竖版画布的阅读形态（已定方向）

| 形态 | 描述 | 产品态度 |
|------|------|----------|
| **B · 一页一屏** | 滑动吸附到每页，像看 Stories / 翻书；每页构图完整 | **理想状态，不强求** |
| **A · 连续卷轴** | 页与页无缝衔接，一直往下滑；最容易转微信长图 | **兜底即可** |

工程含义：两者不互斥。屏幕阅读用 CSS `scroll-snap` 做吸附翻页（B），导出长图时把同一份页序竖叠成连续图（A）。**页序是同一个真源，A/B 只是两种投影。** 这也是 §6「页序真源」的直接受益项。

先按 A 上线可行，B 作为阅读体验升级，不阻塞。

## 8. 模板工具台：不用新建，要提升为主干

### 产品的本质想法（原话大意）

通过模板工具台继续优化所有模板，其他管线或输出统一到这个工具台（现在的临时库 / 模板工坊），未来把所有模板都纳入这个工具管理。在工具台中设计 → 测试 → 管理模板；优秀的模板可以被各个管线统一使用；建立一套适合运维的架构。

### 核实：它已经存在，而且比记忆里更完整

现场 `docs/templates/reserve/`（TDV 设计工坊），静态服 `serve.cmd` → `:18765`，正式合同 [TDV](./PRD-TEMPLATE-DESIGN-VERIFICATION-V1.md) v0.2.1 Conditional Go，W0–W3 现场已做。

| 能力 | 状态 | 现场 |
|------|------|------|
| 新建页型 | 有 | `gallery.html` + `serve.py` POST |
| 微缩预览槽位 | 有 | `gallery.html` ← `faces.js` / `packet.yaml` |
| 0–3 星标注 | 有 | `stars.yaml` + gallery 点星 + 独立禁用名单 |
| 手编成册 | 有 | 8 本 `series/folio-*.yaml`（[RSC](./PRD-RESERVE-SERIES-CABINET-V1.md)） |
| 真图试印 | 有 | `preview.html` · 2 星以上按朝向轮转 / 按系列 / 组锁定 |
| 升格导出检查单 | 有 | `promote.js` |
| lifecycle / 灰度 / 遥测 | **不在工坊** | 归 `/templates-admin`（P13） |

> **所以要做的不是「建一个工具台」，而是「把已有的工具台从旁路提升为主干」。这个区别决定这件事是几个月还是几周。**

### 今天真正卡住的：三处同病

工坊能「设计」和「测试」，但「管理」这一环是手工的。三处相同的病：

| 人写的源 | 运行时镜像 | 同步方式 |
|----------|-----------|----------|
| 工坊 `packet.yaml`（几何） | LTE `page-*.yaml` | `page_promote.py` **单向有损**编译 |
| 工坊 `stars.yaml`（星表） | `editorial_series/page_stars.py` | **手工** sync |
| `docs/templates/card-aspect-3x4/*.md`（ECC 卡片 spec） | `export/card_templates.py` | **手工** sync |

工坊 README 自述：「**薄柜未建，升格未闭环**」。

**缺的不是 UI，是一条自动的编译流水线。** 而且它有个隐性后果：因为每改一次模板都要付一次同步税，会不自觉地少改；少改的结果是模板永远「还没达到理想情况」。这是自我强化的循环，也是「两边模板都不满意」的技术原因，而非审美原因。

### 三套模板世界尚未统一

| 世界 | 现场 | 运行时谁读 | UI |
|------|------|-----------|-----|
| 设计工坊（TDV） | `docs/templates/reserve/` | **引擎不读**（ISO-05 硬拒） | 静态站 `:18765` |
| LTE 活目录 | `travelogue/layout_templates/templates/` | MCS / 渲染 / CI | `/templates-admin` |
| ECC 3:4 卡片库 | `docs/templates/card-aspect-3x4/` + `export/card_templates.py` | 导出管线（Pillow） | 无 |

三套各有一套 authoring / compile / test 路径，schema 互不相通。**ISO-05（运行时不读工坊）应当保留**——工具台可读 reserve，运行时只读编译产物。要统一的是 **元数据层与升格流水线**，不是取消隔离。

## 9. 使用规范：产品指出的第三块短板

### 产品原话（大意）

继续提升必须回到模板设计、**使用规范**和编排成册等功能上。作品集的模板设计有不少改进，但 **使用规范上依然不够**。

### 技术现状：使用规范只存在于文档里，没进运行时

| 层 | 现场 | 状态 |
|----|------|------|
| 人读的使用规范 | 工坊每个页型的 `USAGE.md` | 有，但只给人看 |
| 引擎的使用规范 | `travelogue/layout_engine/usage_rules/`（URO） | **默认关闭**（`config.yaml.example` L352–353 `enabled: false`） |
| 两者之间 | — | **无编译关系** |

已有指标但未成门禁：`pattern_exposure_entropy`、`dense_streak_violation_rate` 写入 trip 的 `layoutMetrics`；盲评门槛 `AC-URO-BLIND`（≥55%）尚未作为 merge gate。

这是 §8「三处同病」的第四例，而且更严重——前三例至少有镜像，这一例连镜像都没接上。

**「使用规范不够」在架构上等于：规范是人写在 `USAGE.md` 里的自然语言，引擎读不到；引擎能读的 URO 默认关着。**

## 15. 补充轮：产品决策节点（2026-08-31 · 同日下午）

### 产品原话（大意）

现在是个产品决策的重要节点：是继续打磨，还是追求极致的产品、推倒重建？

补充事实两条：一、本人为 **非专业程序员**（不懂编程，但有产品思维），当前结果是用 AI 编程能达到的最好局面。二、已经给朋友分享过，反馈见 §15.3。

### 15.0 本节结论（对 §0 的修正）

**不推倒重建，做一次边界明确的换心手术。** 换掉编排层（`mosaic` 搜索 → 系列编排 + 画布参数），保住模板资产与工坊，减掉治理的乘法。

同时，本轮新证据把画布优先级定死：

> **竖版长图是一等画布，16:9 作品集是二等留存物。**

原判断「作品集输出更好」来自 27 寸 2K 显示器上的评测。接收端的实际反馈指向相反方向——**长图是本项目 101 天来唯一获得真实外部正反馈的产物**。

### 15.1 项目体量：一个改变取舍前提的事实

| 指标 | 值 |
|------|-----|
| 首个 commit | 2026-05-21（`Initial commit: Travelogue P0 local workshop.`） |
| 末次 commit（本轮） | 2026-08-30 |
| 周期 | **101 天** |
| commit 总数 | **986**（约 9.8 / 天） |
| `travelogue/` Python | ~139,802 行 / 685 文件 |
| 测试 | 779 文件 / 5,242 用例 |
| 文档 | 30+ 份 active PRD / 验收记录 |
| 开发者 | 1 人 · 非专业程序员 · AI 辅助 |

> **推论：代码是可再生资源，模板与品味不是。**

这条推论是 §15.2 全部取舍的依据。101 天能生成的东西，重新生成一遍的成本不等于它的行数。

### 15.2 「打磨 vs 重建」是假的二选一

两个词都指错了对象。

**「继续打磨」指错**：打磨已经进行很久，产品自评仍「距理想有差距」。瓶颈不在代码质量，在两处摩擦——**没有视觉基线**（§10，无基线的迭代是随机游走）和**手工同步税**（§8 三处同病）。不解开这两处，继续打磨的边际收益只会持续下降。

**「推倒重建」也指错**：它会把项目里唯一真正贵的东西一起扔掉，而那个东西不是代码。

正确的问题是：**哪一层该重建，哪一层该保留。**

| 资产 | 重置成本 | 判断 |
|------|----------|------|
| 76 个 `page-*` + **47** 个 `screen-*` 的几何与审美 | 极高（手画 · 试印 · 标星） | **必须保** |
| 8 本系列的页序编排 | 极高（人编） | **必须保** |
| `stars.yaml` 的品味标注 | 极高 | **必须保** |
| 「算法做不出品味」这个实测结论 | 无价，只能用失败换 | **已内化** |
| ingest / cull / cluster / EXIF / 转码 | 中（脏活已干完） | 保，重写不会更好 |
| `mosaic` 搜索算法 11,696 行 | 已判负收益（§1） | **弃** |
| 140k 行管道代码 | **低**（101 天生成的） | 可重构，但无必要全弃 |
| 双管线专属治理 | 是成本不是资产 | **随管线收敛消失** |

关键观察：**怕丢的其实丢不掉。** 模板资产与工坊都在 `docs/templates/reserve/`，与 Python 管道解耦；真正想扔的（`mosaic`、双管线、治理乘法）本来就该扔。所以「推倒重建」的恐惧感在这张表面前大部分消解。

### 15.3 外部反馈：新证据，权重最高

#### 产品原话（大意）

给朋友分享过，他们都觉得 **长图不错、观看方便**；在旅行途中或结束之后，分享到微信群很好；**他们也会转发给自己的家人**；也会自己保存，作为纪念。是否会发布到媒体平台不得而知，每个人对照片隐私的管理不一样；可以确认的是朋友只会在自己信任的人群中分享。

#### 解读

这段反馈的信息量比表面大得多：

| 反馈 | 含义 |
|------|------|
| 「长图不错」 | **游记管线的旗舰产物已被外部验证。砍它的举证责任极高** |
| 「观看方便」 | 竖版在手机上友好；16:9 在竖屏是细带，无此评价 |
| 「转发给自己的家人」 | **二次传播信号，本项目最强的一条外部信号** |
| 「自己保存作为纪念」 | 留存价值成立，支持作品集的「电子留存 + 偶尔打印」定位（§6） |
| 「只在信任人群中分享」 | **本地优先 / 无账号 / 不上传，从隐私洁癖升级为核心卖点** |

#### 对 §4 的更正

§4 记为「接收端一次都没测过」。准确说法是：**分享侧已有正反馈，且正反馈落在长图上；真正未测的是「作品集在手机上好不好看」。** 后者仍是空白，且 `portfolio-pages.css` 零 `@media` 使它大概率不好看。

因此 §11 的 P0（编译 `stage.variants`）意义变化：它不再是「验证作品集能不能取代游记」，而是「**让二等画布在手机上至少可读**」。取代关系已被这段反馈否掉。

### 15.4 治理体系的重新标定

产品补充「非专业程序员 + AI 编程」这一事实后，本轮口头给出的「治理体系是净负债」判断需要修正。

**对一个不写代码的人，治理体系不是仪表盘装饰，它是方向盘。** 窄缝登记表、所有权 lint、行数棘轮、`.cursor/rules/dual-pipeline.mdc` 是对读不了的代码施加控制的唯一手段；八席评审是把产品思维（本项目真正的强项）转成可执行约束的机制。这套东西正是 101 天 986 commit 没有散架的原因。

所以要减的不是治理，是 **治理的乘法**：

| 项 | 判断 |
|------|------|
| 所有权 lint / 窄缝登记 / `.cursor/rules` | **保** — AI 护栏，非专业开发者的方向盘 |
| 八席评审 | **保，但按决策大小分级** — 不是每个改动都开庭 |
| 行数棘轮（RCL 三核） | **保** — 对读不了代码的人是有效的复杂度代理指标 |
| 双管线专属治理（12 窄缝 + CSS 前缀门 + 3 条 import 契约 + 105 用例） | **随管线收敛自然消失**，这是砍管线最大的隐性收益 |
| 30+ 份 active PRD 并行维护 | **减** — 已收口的合并归档，只留 active 前沿 |
| 模板视觉基线（§10） | **缺失且必须补** — 唯一能让「模板变好没变好」被机器验证的护栏 |

> **治理不是负债，重复才是负债。**

### 15.5 用户定位：这是本节真正的决策点

#### 产品原话（大意）

45 岁左右、摄影爱好者、习惯单反、喜欢为朋友记录生活或旅行；一群朋友出去玩非常低调，只在自己圈子内分享，不会发布到媒体上，只分享给家人、闺蜜、非常信任的朋友。但考虑到上线或开源，这个年纪的用户肯定是少数，**分享欲爆棚的年轻人才是主力军**。是满足这类特定用户群，还是兼顾市场上最多的用户群体？

#### 两段用户

| | **A 段 · 单反摄影爱好者** | **B 段 · 高频自媒体用户** |
|---|---|---|
| 年龄 / 画像 | 40–55、单反、为朋友记录 | 年轻、经营个人 IP |
| 频次 × 批量 | **低频 × 大量**（一趟数百张） | **高频 × 少量**（一顿饭 3–9 张） |
| 照片在哪 | **电脑**（导卡习惯） | **手机** |
| 分享半径 | 信任圈（微信群、家人） | 公域（朋友圈、小红书） |
| 数量 | 少 | 多 |

#### 结论：明确选 A 段，而且这不是妥协

B 段不该做，理由不是「小而美」的浪漫，而是 **产品能力与 B 段需求物理不匹配**：

1. **输入形态不成立**：B 段的照片在手机上。要服务 B 段必须做手机端或云上传，而账号体系、云同步是 [CHARTER](./CHARTER.md) §4.2 明确的 Out of Scope。那是另一个产品。
2. **频次与批量反向**：本产品的价值是「一趟数百张的策展成册，20 分钟出一本」。B 段要的是「3 张即时发」。
3. **核心能力对 B 段空转**：策展的前提是「照片多到需要取舍」。发一顿饭的人不需要有人帮他从 250 张里挑 60 张。**本产品最强的能力对 B 段无用。**
4. **B 段工具市场饱和**：手机修图 App、平台自带模板、拼图 App。他们不缺工具。

反过来，A 段与产品的每一个既有设计严格自洽：

| A 段特征 | 对应的产品设计 |
|---|---|
| 单反、导卡到电脑 | 本地文件夹输入（§4「制作端在电脑上是必然属性」） |
| 一趟数百张 | 策展、分章、去重、封面全部有价值 |
| 低调、只在信任圈分享 | **本地优先、无账号、不上传** 成为卖点而非限制 |
| 为朋友记录、发微信群 | 长图 → 已获外部正反馈（§15.3） |
| 45 岁、买过相机镜头 | 对「一次买断的好工具」接受度高，支撑小而美买断假设 |

> **A 段不是被迫接受的小众市场，是唯一与产品能力自洽的市场。**

#### A 段的隐性放大器：代理型用户

A 段用户是「**为一群人做这件事的那个人**」——一群朋友出去玩，只需要一个人成册。

所以真实覆盖 ≈ **A 段用户数 × 每人服务的朋友数**。朋友是**读者不是用户**：不装软件、不注册、微信里点开即可。这个结构的获客成本极低——每一次分享就是一次曝光，而且是被信任的人推荐的曝光。朋友「转发给自己的家人」正是这个结构在自然运转。

#### 必须说清的代价

选 A 段 = 接受这是一门 **小生意**：几千到几万用户量级、买断制、口碑传播、没有增长曲线。

而「兼顾 B 段」需要云端 + 账号 + 手机端采集，这会直接摧毁 A 段的核心卖点（本地优先、不上传）。**这是真取舍，不存在两全。** 若目标里有「做大」，A 段满足不了；但兼顾 B 段的代价是两段都做不好。

> **§16 修正**：本小节的「小生意 / 用户量级 / 买断制」框架仍是过度商业化的表述。产品目标函数已澄清为 **不指望盈利**（§16.1），因此 A/B 段的取舍论证自动失效——B 段本就是为商业化假设服务的。准确的定位表述见 [§16.8](#168-对-155-定位框架的修正)。

#### 开源渠道与 A 段同向

开源社区里「技术型摄影爱好者 + 隐私敏感 + 愿意本地跑工具」的浓度远高于普通人群。**开源是 A 段的分发渠道，不是 B 段的。** 这条与定位选择互不冲突，可作为 A 段的低成本触达方式。

### 15.6 「极致」的因果链与唯一验收标准

产品自己的实测结论已经给出答案：**极致来自模板和编排，不来自架构。** 架构唯一的作用是决定迭代模板的摩擦有多大。

所以「重建换极致」这条因果链是错的。正确的是：

> **重建的唯一目的，是把迭代模板的摩擦降到接近零。**

这给了「要不要重建」一个唯一且可测的验收标准。今天改一个模板到看见结果的链条：

`改 packet.yaml` → `promote-pages` → `css sync` → 起 Studio → 找一趟 trip → 重渲染 → 肉眼比对（**且无 before/after**）

**若重建后这条链变成「改模板 → 看到 before/after 对比图」，则值得。若只是把 140k 行换成更漂亮的 80k 行而这条链没变，则不值得**——那只是换了个更整洁的地方继续随机游走。

### 15.7 八周排程建议（仅建议，不立项）

| 周 | 做什么 | 为什么在这个位置 |
|----|--------|------------------|
| 1 | P0（`css_gen` 编译 `stage.variants`） | 让二等画布在手机上可读；不再承担「取代游记」的举证任务（§15.3） |
| 2–3 | P1 视觉基线（每 template id 绑固定照片集 + before/after） | §15.6 的唯一验收标准就落在这里；所有后续模板工作的地基 |
| 4 | **拍板**：竖版模板族怎么来、`mosaic` 何时退、治理减到哪 | 有基线之后才拍，且此时手机端可读性已知 |
| 5–8 | P2–P4（使用规范进运行时、系列性格维度、升格闭环） | 顺序见 §11 |
| 之后 | P6 产品面下线 → 观察 → P7 删代码 | 不可逆的放最后；守卫脚本最后删（§11 P7） |

> **拍板点在第 4 周，不在今天。** 今天信息不足，而补足信息只需三周。为省这三周而现在拍板，是本决策里唯一真正不可挽回的错误。

### 15.8 两条最后的建议

**最想劝住的一件事：不要因为「架构不够优雅」而重建。** 现有架构确实繁复，但繁复的来源是双管线加治理乘法，两样都能在不重写代码的前提下删掉。删完之后剩下的核其实可用——ingest、cull、cluster、封面、Studio 壳这些脏活已经干完，重写一遍不会更好，只会再花 101 天。

**最该守住的一件事：定位已经由外部反馈选好了。** 最初的目标是「把自己旅行的照片集做成游记，分享给一同旅行的朋友」——这个目标自带验收标准，而 §15.3 的反馈说明它 **已经达成**：朋友觉得长图不错、观看方便、会转发给家人。

所以真正的任务不是推倒重建去追一个更抽象的「极致」，而是：**把这个已被验证的产物，做得更精致、更可靠、更快迭代。** 这正好就是 §11 的 P0–P4。

## 16. 目标函数与收口（2026-08-31 · 第三轮）

### 产品原话（大意）

这个项目感觉不具备商业化前景，它是一个针对少数群体的好用工具，更适合开源。小红书之类的媒体平台导出，是做了很多次竞品分析后发现「**只有能够为社交平台提供素材的工具，才会有关注度和流量，也才有可能商业化**」，索性就加了那些导出模式，作为弥补产品的丰富性。

作为个人开发者，**并不指望这个产品有盈利能力**，更在乎「自己独立制作了一款应用，标志着自己的想法变成了现实」，这让人有很大的成就感。可以接受每月 200 美金的 AI 订阅费用用于开发，**也没有时间限制**，可以自己慢慢做。但**比普通独立开发者有更高的要求，不愿意求快，不愿意做一个 demo 或不成熟的产品就拿去炫耀**；想真正做一款有用的小工具。

### 16.0 本节结论

1. **功能冻结**（产品本轮已定）：维持现有功能，不再增加。
2. 商业化动机链断裂：为社交平台准备的导出模式失去了原始理由，但产品判断「朋友偶尔也需要、复杂度增量可接受」，故 **保留但不再投入**。
3. 真实约束不是时间也不是金钱，是 **单人可掌控的复杂度上限**。
4. 开源前必须先精简，顺序不可反。
5. **最大的风险不是失败，是永远不结束。** 需要写下一句能背下来的 v1.0 定义。
6. 「高要求」必须落成 **可判定门槛**，否则会变成永不满意、永不发布。

### 16.1 目标函数（这是本备忘录全部建议的重新加权依据）

| 维度 | 值 |
|------|-----|
| 盈利 | **不指望**（明确放弃） |
| 用户量级 | 不作为指标 |
| 首要回报 | **成就感** —— 「想法变成了现实」 |
| 时间约束 | **无** |
| 资金约束 | ~$200/月 AI 订阅，可承受 |
| 质量要求 | **高于普通独立开发者**；拒绝 demo 级炫耀 |
| 分发路径倾向 | **开源** |
| 自我定义 | 「真正做一款**有用的小工具**」 |

**推论：前几轮所有含商业假设的论证（市场大小、用户段取舍、增长曲线）自动降权。** 唯一保留的商业相关结论是「不做云端 + 账号 + 手机采集」——但理由从「会摧毁卖点」变成了更简单的「不需要，且会突破复杂度上限」。

### 16.2 商业化动机链断裂

产品原话已完整给出这条链：

> 只有能为社交平台提供素材的工具 → 才有关注度和流量 → 才有可能商业化

**链条的终点（商业化）被主动放弃，则整条链失去承重意义。**

而且更关键的是段位互斥：A 段（§15.5）低调、只在信任圈分享、不发媒体平台——这是产品与朋友的实际行为（§15.3）。因此 `小红书 / 公众号` 这类公域导出，**在目标用户里的常规使用者接近于零**。

第二个动机「弥补产品的丰富性」也需要被点明：**丰富性不等于有用性。** 对一个自我定义为「有用的小工具」的产品，形态越多越弱——每个形态都在稀释主路径的打磨精力。当前「模板还不够精致」的体感，部分来源就是注意力被六个平台分摊。

### 16.3 产品裁决：冻结不增，保留不删

产品本轮判断（原话大意）：

> 维持现有的功能，不再增加。虽然有多重导出模式，但我觉得那些也是现在朋友需要的，只是不那么频繁；在没有增加多少复杂度的情况下，我可以接受。毕竟图片的使用场景非常丰富。

**本备忘录接受这个裁决。** 「冻结不增」已经拿到了收缩的大部分收益，删与不删是次要问题。

#### 导出层实测体量（供未来复核「复杂度增量」这个假设）

| 项 | 实测 |
|----|------|
| `travelogue/export/**` Python | **34 文件 / 9,535 行** |
| ECC 卡片规格（`docs/templates/card-aspect-3x4/`） | **29 文件** |
| 导出相关测试文件 | **54** |
| 导出相关 PRD / 验收 / 实施文档 | **16 份** |

#### 结论：产品的直觉大体成立，但有一处例外

**成立的部分**：9,535 行里的大头是 **长图（longshot）**——16 份文档中约 6 份是长图专属（`LONGSHOT-2.0` / `ENG-SUPPLEMENT` / `COOPERATIVE-CANCEL` / `M14-shelf-save` / `ACCEPTANCE-LONGSHOT` / `CROSSING-LONGSHOT-GATE`）。长图是核心且已被外部验证（§15.3）。社交平台导出建在这套既有基础设施之上，**边际成本确实低于总量所暗示的规模**。

**例外**：**ECC 是第三套独立的模板世界。** 它有自己的 29 份 `.md` 规格、自己的 3:4 画布、自己的 Pillow 渲染器，且 `docs/templates/card-aspect-3x4/*.md` → `travelogue/export/card_templates.py` 是 **手工同步**——即 §8「三处同病」中的一处。

这一处有 **持续成本**，不是一次性的：将来做升格闭环（§11 P4）时，ECC 要么一并纳入统一 catalog，要么成为一个永久的手工同步缺口。

**建议（不强求）**：ECC 冻结在当前状态，**不再新增卡片规格**。若日后 P4 落地，再决定是纳入还是就地封存。这样既尊重「朋友偶尔要用」，也不让第三套模板世界继续长大。

### 16.4 真实约束：可掌控的复杂度上限

时间无限、资金可承受、无 deadline。那么唯一的约束是：

> **一个非专业程序员 + AI，能够理解并掌控的复杂度上限。**

治理体系是方向盘（§15.4），但方向盘本身有容量——30+ 份 active PRD 已在可追踪的边缘，窄缝 12 条上限 14，加上棘轮、八席、验收记录、狗粮协议。每增加一个形态，治理负担是 **乘法** 增长。

这条推论直接接住产品自己的高要求：

> **一个你无法完全掌控的系统，你没有办法判断它是否可靠。** 而「可靠」是产品自定的质量标准之一。

所以减少形态数量对本项目 **不是效率问题，是可控性问题**。判断任何决策的统一标尺应当是：**这会让项目更容易还是更难被我一个人握住？** 而不是「这值不值这个钱」。

### 16.5 开源：先精简，再开源

开源意味着代码会被人读。今天外部人进入会遇到：140k 行、30+ 份 PRD、双管线、12 条窄缝、八席评审记录，以及一整套私有中文术语——窄缝、棘轮、过河、票根、开章、气口、薄柜、金样、狗粮。

这些术语对本人与 AI 高效，但对外部贡献者是 **入门成本**，不是代码质量问题。

因此开源路径下，「有用的小工具」的标准需追加三项：**别人能不能读懂、能不能装上、能不能改。**

**顺序不可反**：先精简再开源。反向操作会背上向后兼容的心理负担——哪怕只有三个 star，也会不好意思删东西。**现在删是自由的。**

### 16.6 「完成」的定义：本节最重要的一条

产品的首要回报是「想法变成了现实」的成就感。但对一个 **无 deadline、无盈利指标、无用户增长指标** 的项目：

> **最大的风险不是失败，是永远不结束。**

症状已经出现：101 天 / 986 commit / 形态在竞品驱动下扩张 / PRD 累积至 30+ / 而「什么叫做完了」从未被写下。项目有向「以开发本身为目的」漂移的倾向。这本身不坏（作为爱好完全正当），但它与「做一款真正有用的小工具」存在真实张力：后者需要收口，前者需要永远有下一个功能。

**「想法变成现实」需要一个可以说「做完了」的时刻。没有这个时刻，成就感永远无法兑现——项目会永久停留在「在做」。**

#### 待办：写下一句能背下来的 v1.0 定义

**2026-09-01 已定稿**，以 [收敛任务清单.md](./收敛任务清单.md) `R0-01` 为准：

> **用户选定一组照片，系统自动编排成一张可直接分享的长图；分享出去。**

备忘录原参考稿（「20 分钟 / 网页 / zip」）作废，细节改由 `R0-04` 写门槛。然后把现存每一样东西对着这句话过一遍，不在其中的标 `post-1.0`。这句话同时是验收标准和「允许自己说完成」的那道线。

**注**：产品本轮已选择「功能冻结、维持现有」，因此 v1.0 定义的作用不是删功能，而是 **界定「打磨到什么程度算做完」**。

### 16.7 「高要求」的陷阱

「不愿求快、不做 demo 炫耀」是好的自我要求。但它的反面风险是 **永远不发布**，且对一个没有外部用户的项目，高标准 **无法校准**——不知道什么算「够好」。

当前唯一的校准点是 §15.3 的朋友反馈：长图不错、观看方便、会转发给家人、会自己保存。

> **标准可能已经达到了，只是本人不相信。** 27 寸屏上看到的是「模板还不够精致」，朋友在手机上看到的是「这个不错，转给家人」。这不是质量差距，是评价视角差距——而产品的成败在后者。

**建议**：把「高要求」落成 **可判定门槛**，而非一种感受。

| 表述 | 可判定？ |
|------|----------|
| 「够精致」 | ❌ 永远可以再精致一点 → 永远发不出来 |
| 「**123** 个模板在视觉基线对比下均无明显缺陷」 | ✅ |
| 「三趟真实照片各出一本，朋友端无一处明显破版」 | ✅ |

这也是 §11 把 P1（视觉基线）排得极靠前的深层理由：

> **它不只是工程设施，它是把「我觉得还不够好」变成「这一项已达标」的唯一工具。**

### 16.8 对 §15.5 定位框架的修正

§15.5 的结论（选 A 段）**方向正确，但论证过度商业化**。

准确表述应为：

| §15.5 原表述 | §16 修正后 |
|--------------|-----------|
| 「选 A 段 = 接受一门小生意」 | **不指望盈利，因此无需论证市场大小** |
| 「兼顾 B 段会摧毁核心卖点」 | 仍然成立，但主要理由改为 **会突破复杂度上限** |
| 「A 段用户量级几千到几万」 | 不作为指标 |
| 「买断制、口碑传播」 | 降为 post-1.0 的开放项，非当前决策输入 |

**最终定位表述**：

> 服务本人及与本人同类的使用者（单反、导卡到电脑、一趟数百张、只在信任圈分享），以 **开源** 分发。不需要用户量级论证，不需要增长曲线，不做云端 / 账号 / 手机采集。

A/B 段的取舍论证自动失效，因为 B 段本就是为已放弃的商业化假设服务的。

**这让整件事轻松很多：不需要说服任何人这个市场有多大。**

## 18. 假设从零委托：专业开发者视角的设计

### 场合

产品提问：「假设你作为一个专业的开发者，面对我这样的需求，假设委托给你来设计与开发实现，你会怎么做？」

本节是 **思想实验**，目的不是提议重写，而是 **反照现有架构里哪些是本质、哪些是历史**。结论见 §18.7——从零设计与 §17 的收敛终点几乎是同一个架构。

### 18.0 核心立场：交付的不是引擎

接这个委托的第一次会议就要讲清楚：

> **这个产品的质量不在代码里，在模板和页序里。而模板和页序是客户的活，不是开发者的活——开发者供不了客户的品味。**

因此开发者职责重新定义为：**把客户迭代模板的循环压到最短，然后让路。**

### 18.1 预算分配

| 项 | 占比 |
|----|------|
| 引擎 | 30% |
| **创作工具 + 视觉基线** | **40%** |
| 输出与打磨 | 30% |
| **算法** | **0%** |

这个分配对客户通常难以接受（「我花钱请你写算法」），但对本需求是唯一正确的分配——而本项目的三个月已经把它证明了（§2、§3）。

### 18.2 引擎：要小、要笨

品味住在人写的模板与序列里，则运行时只剩三件事：**选一套序列 → 把照片装进槽位 → 渲染**。约 2,000–3,000 行。

对照现状：`editorial_series` = **2,298 行**。

> **这是个漂亮的巧合，说明现有实现已经摸到了正确的规模。** 而 `mosaic` 的 11,696 行在做一件从零设计时不会做的事。

### 18.3 第一天就定死的四条规矩

#### 一、页序是唯一真源，所有输出都是投影

```
照片 → 筛选 → 页序 → { 竖版网页 · 长图 · zip · 16:9 留存 }
```

页序之前是数据削减，页序之后全是渲染。**任何输出都不许通过截取另一个输出得到。**

对照现状：页图靠拍预览 DOM，把两个产物耦合在一起。从零设计不会这么做——页图与长图都从页序直接画。

#### 二、画布是数据，不是命名约定

模板自行声明支持哪些画布、以及每个画布下的几何。将来加 3:4 / 4:5 / 印刷跨页，改的是 **数据**，不是代码。

对照现状：`css_gen.template_family()` 靠字符串前缀 `page-` 判断族属，是「第二种画布来晚了」的典型痕迹。**但更能说明问题的是：`stage.variants` 这个正确的抽象已经写在 schema 里了（§5），只是编译器没实现——直觉早就对了，只是那一版实现赶不上直觉。**

#### 三、确定性靠构造，不靠测试

同一文件夹 + 同一版模板库 = **逐字节相同**的输出。不读时钟、不依赖集合迭代顺序、不用随机 tie-break、所有排序均有显式 key，输出盖「模板库哈希 + 引擎版本」戳。

这不是洁癖，它是视觉基线成立的前提：只有输出确定，「改模板有没有碰坏别的」才有答案。

#### 四、视觉基线属于第一周，不是后期补的设施

对靠品味取胜的产品，**回归测试就是截图**。

固定 5 组照片集（人物为主 / 风景为主 / 杂乱 / 稀疏 / 超量），每个模板、每套序列都有参考图进仓库，改模板就看 diff。

> **从零设计会在做第二个模板之前先做这个东西。** 从第 2 个模板到第 150 个模板，没有基线则每一步都是随机游走——这正是现状（§10），也是「优化很久但感觉没到位」的技术根因。

### 18.4 明确不做

- **搜索 / 优化层**：永远不做
- **多平台导出矩阵**：一个竖版产物 + 一个归档 + 一个留存；将来加平台 = 一个模板 + 一个画布，不是一个子系统
- 账号 / 云端 / 手机采集
- 运行时 AI（创作时可用 AI 帮写文案，人审）
- **单管线的治理机械**：现有 12 窄缝、所有权 lint、CSS 前缀门、105 条隔离用例的根因是「有两条管线」。一条管线的护栏约为现在的 1/5——而那 1/5 仍然要做，因为客户读不了代码（§15.4）

### 18.5 排期逻辑：按「做错了有多贵」排序

不按依赖关系排，按错误成本排。

| 阶段 | 内容 |
|------|------|
| 第 1–3 周 | **最薄的端到端切片**：文件夹进 → 8 页写死版式 → 手机上竖着能读。无筛选、无聚类、无模板库 |
| 第 4–6 周 | 创作工具 + 视觉基线（**在模板库变大之前建好**） |
| 第 7 周–第 6 月 | 客户主导、开发配合，长模板库与序列。**最长的一段，也是质量的全部来源** |
| 最后 | 筛选 / 聚类层 |

两条要点：

- **先证明阅读体验**，因为它是唯一后期修不回来的东西
- **筛选层故意最后做**：第一阶段只做粗糙版（EXIF 时间分桶 + 基础去重），只有当模板工作暴露它是瓶颈时才投入。这一层「够用就真的够用」，且最容易被过度工程

### 18.6 对 §17 的一处修正建议（待产品裁决）

按 §18.3 第一条重看 §17，存在一处真实分歧：

> **P5「页序真源」在从零设计里是第一天的地基，在 §17 里排在第五位。**

两个具体后果：

1. **「长图从页序竖叠生成」是唯一被外部验证过的产物（§15.3）的替代实现方案。** 它排在 P5，意味着核心产物的架构升级要等很久。
2. **P1 视觉基线会因此变难。** 页序若是真源，可拿一个合成页序直接渲染单个模板，不必跑完整 trip；页序若不是真源，每次基线都要走完整管线。**P5 提前一部分，P1 会变便宜。**

#### 建议拆分

| 原 P5 条目 | 建议位置 |
|-----------|---------|
| **页序升为真源**（主要是数据结构与契约） | **提到 P1 之前** |
| 页图学 ECC（Pillow 直出） | 留在 P5 |
| 长图从页序竖叠生成 | 留在 P5 |

**未拍板。** 若采纳，§17 的阶段零之后需插入一条「页序契约定稿」。

### 18.7 诚实的对照

从零按上述设计，规模大约落在 **15,000–25,000 行**，而非 139,802 行。

但必须说清两件事：

**第一，之所以能这么设计，是因为这三个月已经把答案证明出来了。** 一个不知道「搜索做不出品味」的开发者，接到这个委托一定也会先写那个搜索引擎——因为它是最显然的尝试，而且纸面上看起来更聪明。

> **那 11,696 行不是浪费，它是发现这个设计所必须付的学费**；而且是产品亲手付的，所以现在对它有确信，而不只是听人说。

**第二，不需要重建才能到那个形状。** §17 的 P0–P7 收敛到的架构与从零设计几乎同一个，差别只是它保住了：

- **123** 个模板的几何与审美
- 8 套序列的页序编排
- `stars.yaml` 里的品味标注

**而这三样恰恰是从零开始时最缺、也最贵的东西（§15.2）。**

### 19.2 最严重的更正：§5 结论作废

原 §5 主张「多画布的声明层已建好，缺的只是编译器，P0 是一处改动」。**三句全错。**

真实情况：variant 只声明画布 **比例**，不声明画布 **构图**。若真去编译它，列宽行高沿用顶层 stage，产出是「把 16:9 网格塞进 9:16 盒子」——槽位极端瘦高，照片被暴力 cover-crop。

> **危害不是「没用」，而是「会看起来做完了」。** 能跑、能过 schema 校验、有媒体查询的手机版会给出错误信心，并消耗掉验证竖版的那一次机会。

因此接受评审的替换方案：**P0 改为竖版试点——先扩 schema、保住模型字段、清渲染硬编码，然后只做 3 个代表模板 + 1 套 8 页系列的真实 9:16 几何。** 见 §17 P0（已重写）。

### 19.3 一个反向发现：§2 的论点变强了

更正后的模板均长：

| 模板族 | 文件数 | 总行数 | 平均行数/个 |
|--------|--------|--------|-------------|
| `screen-*.yaml` | 47 | 3,208 | **68.3** |
| `page-*.yaml` | 76 | 10,203 | **134.2** |

倍数由初版的 1.68 倍升至 **1.96 倍**。**「搜索算法迫使模板保持通用」这个论断的证据强度提高了**，而不是降低。

### 19.4 评审优于原备忘录的三处 · 建议采纳

| 项 | 评审的主张 | 为什么更好 |
|----|-----------|-----------|
| **LayoutPlan 提前至阶段 1** | 优先把现有 `chapters[].screens[]` 升级为稳定 `LayoutPlan v1`（页序、slot→asset、fit/crop、模板版本、`catalogHash`），**不再造第三套平行数据** | 与 §18.6 独立得出同一结论（两条独立推理相撞，可信度高）；且比「页序是真源」更可执行 |
| **性格由用户显式选** | 首版只给「均衡 / 人物 / 风景」三个可见选项，默认均衡；算法只建议、不暗中决定 | 接住产品实测「多维度算法组合效果有限」；保住可解释性；优于原 P3 的 `match.py` 自动选档 |
| **容量档由母序列裁切点派生** | 一份母序列 + 人工裁切点 → 派生厚度档，而非 8 厚度 × N 性格 | 直接消除 §3 埋下的 SKU 爆炸隐患 |

另：评审的 v1.0 门槛比 §16.7 更可判定，建议整体替换。其中 **「用户手工调整在重渲染后不丢失」** 是原备忘录完全遗漏的真实需求（精修持久化）；**「同输入 + 同 catalogHash → 同 LayoutPlan」** 把 §18.3 的确定性规矩落成了验收条款。

### 19.5 需要给评审补的两点

**一、截图基线不是「扩展」，是从零建。** 评审的「应扩展而非另建体系」会低估工作量——只有一张书法特例，没有体系。这仍是整条路线里最关键的一件基础设施（§10 判断维持）。

**二、「无 UI 浏览器渲染面」不是纯胜，是取舍。** 用它替代 Pillow 直出方向正确——`page-*` 的排版语义确实在 CSS 里，Pillow 重画等于重写 CSS 引擎。但代价须写明：**仍依赖 Playwright / Chromium**，即打包体积、启动时间、跨平台稳定性都还在。对一个「干净 Windows 环境能装能跑」的开源工具，这个代价不小。

正确的收口表述应为：

> **CSS 是排版真源这件事必须承认；Pillow 直出只适用于 ECC 那种简单槽位的产物，不适用于 `page-*`。**

这同时修正了 §6 与 §16.9 中「页图学 ECC」的乐观表述。

### 19.6 本节的方法论意义

本轮六条反驳中五条成立，其中一条推翻了备忘录的旗舰建议。原因不是推理错误，而是 **推理建立在未经代码核验的探查报告之上**（初版模板数来自子代理统计，未排除构建产物；`variants` 的判断只看了 schema 与 `css_gen`，未追 `models.py` 与渲染层）。

> **教训：凡是要落成实施动作的技术判断，必须追到数据模型与渲染端，不能停在 schema 与声明层。**

这条对后续所有 PRD 立项同样适用。
